The 60-second case

A valid Zarr header can still be a lie. The confirmed PHerc0814 pyramid opens normally, but all six levels have no chunks and silently read as zeros. That failure can waste training runs or invalidate downstream segmentation and ink work without throwing an error.

Find

957 S3 roots audited in about five minutes; one live structural corruption case independently re-confirmed on September 30.

Prove

A direct zarr-python read returned all zeros without error; a populated control returned 64,498 nonzero voxels.

Prevent

zpa-gate turns the finding into a publish-time CI failure: defective root exit 1, clean sibling exit 0.

Evidence is committed and reproducible; the page links every headline claim to a repo artifact below.

(1) Which scroll data did you work on?

The entire open-data surface, on both public stores:

  • S3 bucket (s3://vesuvius-challenge-open-data): 957 Zarr pyramid roots discovered by full bucket crawl, spanning PHerc0814, PHercParis4, PHerc186 and community uploads.
  • dl.ash2txt.org: the 241-root set behind villa issues #1755–#1760, re-audited for a 20-day regression check.
  • Deep dives: the defective PHerc0814 surface volume (villa #1892), the known silent-zero volumes, and 64 same-named volumes present in both stores.

(2) How does it increase the probability of reading the scrolls?

Ink detection, segmentation, registration and interactive viewing commonly consume reduced pyramid levels rather than repeatedly reading the full-resolution volume. A level whose header is valid but whose chunks are missing can return plausible all-zero voxels with no error — silent corruption that burns compute and can mislead downstream analysis. This contribution does not merely report that risk; it turns the check into a reproducible pre-publication gate:

  • Finds live corruption before anyone trains on it. The audit independently confirms the header-only PHerc0814 surface volume (villa #1892, all 6 levels header-only, reads silently return zeros) is still live in the bucket — and names its two populated sibling renders as safe alternatives. The new chunk-content probe then caught a second live case the header audit cannot see: 7 of 8 levels of other/dev/meshes/20231022170900-ome.zarr decode to all zeros while L0 holds real mesh data.
  • Stops new corruption at the door. zpa-gate is a publish-time metadata gate that fails closed on structural defects (high severity by default), with GitHub Actions annotations for CI.
  • Proves defects don't self-heal. The 20-day regression found zero of 18 defective pyramids repaired — so catching defects before publish is the only point of leverage, which is exactly what the gate provides.
The fix ships with the repo. zpa-gate audits roots before they publish and fails closed — the gate can block this defect class before publication when used. Proven end-to-end 2026-09-30 (artifacts/2026-09-30-gate-proof/): rejects the defective PHerc0814 root (exit 1), passes its clean sibling (exit 0).

(3) What does it enable that was not possible before?

  • Full-bucket S3 coverage added to this auditor. The upstream tool only covered dl.ash2txt.org; this fork adds anonymous S3 discovery/auditing and has now run across 957/957 discovered roots header-only in ~5 minutes. This is the evidence base for the live PHerc0814 finding.
  • Zarr v3 support. v3 bare arrays were misreported as NOT_A_ZARR_GROUP; now correctly classified as BARE_ARRAY with shape/chunks/dtype. All 70 v3 pyramids audited clean.
  • Chunk-content probing (zpa-scan-chunks): closes the next silent-corruption class — chunks that exist but decode to all fill_value — via sampled decode (v2/v3, raw/Blosc/sharded, and now volcomp: all 64 scroll volumes on dl.ash2txt.org decoded with a vendored libvolcomp, 384 levels probed, 0 present-but-empty).
  • Mirror-fidelity evidence. The 64 same-named volumes are format migrations, not copies (S3: v2/128³/raw; dl: v3/1024³-sharded/volcomp, quantization noise only) — reproducibility must pin the store, not just the name.
  • A public, living data-health dashboard generated from audit artifacts, so anyone can see bucket health at a glance.

Distinct from the August 2026 awarded scroll-data-audit work. The official winners page describes that project as defect-hunting across the open-data catalog and volume-cartographer with catalog metadata checks and VC3D fixes. This submission complements it at a different layer: Zarr pyramid structure, chunk presence/content, mirror fidelity, and a CI gate that can reject a bad published root before downstream use.

Why this matters for the 2027 Grand Prize pipeline

This project is infrastructure, not an unrolling claim. The 2027 Grand Prize requires a reproducible pipeline that can segment/unroll an entire scroll and then render legible ink. Those stages depend on trustworthy volumes, surfaces and multiscale reads. zarr-pyramid-audit supplies a cheap integrity boundary before expensive segmentation or ink inference and a machine-readable trail for reproducing exactly which store/root was used.

That trail is consumed downstream: ScrolIQ's scroliq-provenance gate requires a zarr_audit record for the exact eligible CT volume (tool name, audit-manifest SHA-256, and a root naming that volume), and its Grand Prize probe protocol makes this audit Stage A.
